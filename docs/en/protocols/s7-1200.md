## 0. 30-second overview

```jsonc
// s7-1200.json top-level 7 fields
{
  "transport":     "Tcp (port 102 given by the device side)",   // 1. transport layer
  "framing":       "LengthField at offset 2 (= TPKT length field)", // 2. framing
  "dataByteOrder": "BigEndian",                     // 3. S7 data-region byte order
  "inputs":        "StartByteAddress / ByteCount / BitOffset / DBNumber / Area / TransactionID",
  "outputs":       "AddrLo / AddrMid / AddrHi (byte address → S7 bit-address conversion)",
  "handshake":     "COTP_CR → S7_Setup (two steps)", // 6. session establishment
  "operations":    "8: Read/Write × Bit|Word|DWord|Real"
}
```

**MyProt's S7 config = a "byte-stream script"**:

| Config location | Which S7-spec layer it maps to |
|------|------|
| `framing` | TPKT header (4 bytes) length-field location |
| `handshake[0]` | COTP Connection Request → Connection Confirm |
| `handshake[1]` | S7 Setup Communication (negotiate PDU length) |
| `operations[*].requestTemplate` | fixed header + `Read Var` / `Write Var` parameter region + address region |
| `operations[*].responseParser` | return-code judgment + data-region start |
| `outputs.AddrHi/Mid/Lo` | **byte address → S7 bit address** (`byte<<3`) conversion |

**One-sentence value of this adaptation**: in the tag you only write a **byte address** (`DB1.DBD4` → `StartByteAddress: 4`), and MyProt converts it into S7's three-byte bit address `00 00 20` ✅ (`4 × 8 = 32 = 0x20`).

## 1. Frame structure recap (MyProt view)

### 1.1 Three nested layers

All S7-1200 messages (handshake and read/write alike) share one skeleton:

```
┌────────────┬─────────┬──────────────────────────────────────────┐
│ TPKT (4B)  │ COTP(3B)│ S7 PDU (10B header + param region + data region) │
│ 03 00 LLLL │ 02 F0 80│ 32 <ROSCTR> ...                          │
└────────────┴─────────┴──────────────────────────────────────────┘
  ↑ framing takes the length from here
```

| Layer | Bytes | Description |
|------|:--:|------|
| TPKT | `03 00 <total-len 2B>` | fixed header `03 00`; **length = whole-frame byte count (incl. these 4 bytes)** — hence `lengthIncludesHeader: true` |
| COTP | `02 F0 80` | data PDU: `02`=header length, `F0`=DT, `80`=TPDU-NR and EOT |
| S7 | `32 <ROSCTR> …` | `32`=S7comm protocol id; `ROSCTR`: `0x01`=Job(request), `0x03`=Ack_Data(response) |

### 1.2 TPKT length field vs `framing` mapping ✅

```jsonc
"framing": {
  "type": "LengthField",
  "lengthFieldOffset": 2,     // the TPKT length field starts at byte 2
  "lengthFieldLength": 2,     // spans 2 bytes
  "lengthIncludesHeader": true,  // ★ the length value includes the 4-byte TPKT header (S7-specific)
  "headerLength": 4,             // ★ header length = TPKT 4 bytes
  "byteOrder": "BigEndian",
  "lengthAdjustment": 0,
  "maxFrameSize": 4096        // MyProt-side receive ceiling (unrelated to the PDU negotiated with the PLC)
}
```

**How it's used**: read the length-field value `N` → the whole frame is exactly `N` bytes (no add/subtract header) ✅

- read 1 WORD request: `03 00 00 1F` → `0x1F = 31` bytes ✅ (6-2)
- write 1 REAL request: `03 00 00 27` → `0x27 = 39` bytes ✅ (6-19)
- write 1 bit request: `03 00 00 24` → `0x24 = 36` bytes ✅ (6-28)

> Contrast with Modbus: Modbus has `lengthIncludesHeader` = `false` and `headerLength: 6` (the length counts only the PDU). **The framing difference between the two protocols is exactly these two lines** — which is why framing is the easiest field to misconfigure and the earliest to be caught (save-time trial render, see [ADR-0012](../../adr/0012-derivedlength-template-primitives-and-trial-render.md) *zh*).

### 1.3 Handshake: establish the session in two steps

**Step 1 — COTP Connection Request (CR)**, whole frame 22 bytes (`0x16`) 🧮:

```
03 00 00 16             TPKT: total length 22
11 E0 00 00 00 01 00     COTP CR: header len 0x11, type 0xE0(CR), dest-ref 0000, src-ref 0001, class 00
C1 02 01 00             parameter C1 (src TSAP)   len 2 value 01 00
C2 02 01 02             parameter C2 (dest TSAP)  len 2 value 01 02   ← ★ rack/slot encoding; change this line for another model
C0 01 0A                parameter C0 (TPDU size)  len 1 value 0A = 1024 bytes
```

Judgment: `validCondition: "resp[5] == 0xD0"` — i.e. expect a **CC (Connection Confirm, 0xD0)** ✅ (offset 5 is the COTP type byte 🧮)

**Step 2 — S7 Setup Communication**, whole frame 25 bytes (`0x19`) 🧮:

```
03 00 00 19             TPKT: total length 25
02 F0 80                COTP DT
32 01 00 00 00 01 00 08 00 00   S7 header: Job + reference 0001 + param len 8 + data len 0
F0 00 00 08 00 01 03 C0         params: func 0xF0(Setup) + reserved + MaxAmQ(8) + MaxAmQ(1) + negotiated PDU 03C0=960
```

Judgment: `validCondition: "resp[8] == 0x03"` — i.e. the response's `ROSCTR = 0x03` (Ack_Data) ✅

> ⚠️ In the handshake template, `C2 02 01 02` (dest TSAP) and `03 C0` (960-byte PDU) are **values for the S7-1200**; for a 300/400 or a non-default rack/slot you must edit these two spots per the real device (this repo does no model auto-adaptation).

### 1.4 Read Var request layout (field by field) ✅

Taking `ReadVarWord` as the example (`StartByteAddress=4`, `ByteCount=2`, `DBNumber=1`, `Area=132`):

| Offset | Bytes | Field | Value source |
|:--:|------|------|------|
| 0..3 | `03 00 00 1F` | TPKT | constant + `{PDULength}`? No — a read op is a **constant 0x1F** (read request is fixed-length 31) |
| 4..6 | `02 F0 80` | COTP DT | constant |
| 7..10 | `32 01 00 00` | S7 header: protocol id + ROSCTR(Job) + reserved | constant |
| 11..12 | `{TransactionID:X4}` | PDU reference | `source=auto`, `autoIncrement` (seed=1) |
| 13..14 | `00 0E` | parameter-region length = 14 | constant (fixed for read requests) |
| 15..16 | `00 00` | data-region length = 0 | constant (read request has no data region) |
| 17 | `04` | function code = Read Var | constant |
| 18 | `01` | item count = 1 | constant (single tag, single item) |
| 19 | `12` | variable-spec type = S7ANY | constant |
| 20 | `0A` | following address-spec length = 10 | constant |
| 21 | `10` | addressing syntax id = S7ANY (absolute) | constant |
| **22** | `03/04/06/08` | **transport size TS** | constant, see [§4.3](#43-two-transport-size-tables-do-not-mix-them) |
| **23..24** | `{Length:X4}` | **element count** | `derivedLength`: `ByteCount/2`, `ByteCount/4` or `ByteCount` ✅ (6-4/6-7/6-11/6-14) |
| 25..26 | `{DBNumber:X4}` | DB block number | tag `variables.DBNumber` (example = 1) |
| 27 | `{Area:X2}` | area code | tag `variables.Area` (example = 132=DB) |
| 28 | `{AddrHi:X2}` | S7 address high byte | `(byteAddr*8)/65536` ✅ (6-12: 8192→`01`) |
| 29 | `{AddrMid:X2}` | S7 address mid byte | `((byteAddr*8)/256)%256` ✅ (6-8: 1000→`1F`) |
| 30 | `{AddrLo:X2}` | S7 address low byte | `(byteAddr*8)%256` ✅ (6-5: 4→`20`) |

**Total length is always 31** ✅ (6-2) — the read op's TPKT length is independent of element count (the length info lives at 23..24).

### 1.5 Read Var response layout 🧮

```
0..3    TPKT (length field = whole-frame length)
4..6    02 F0 80 (COTP DT)
7       32        protocol id
8       03        ROSCTR = Ack_Data   ← handshake step 2 judges exactly this byte
9..10   00 00     redundancy id
11..12  PDU reference (echoes the request's TransactionID)
13..14  parameter-region length = 00 04
15..16  data-region length = 00 04 + 2×N (N = element count)
17      error class    ← not parsed by this repo
18      error code      ← not parsed by this repo
19      04        function code (Read Var)
20      01        item count
21      FF        return code: 0xFF = success     ← ★ validCondition: resp[21] == 0xFF
22      04/06/08  data-region transport size
23..24  length (BIT type counts in bits, others count elements)
25..    data region (payload)                    ← ★ dataStartIndex = 25
```

From this you can directly derive: **read 1 WORD response = 25 + 2 = 27 bytes**; **read 1 DWORD/REAL = 25 + 4 = 29 bytes** 🧮

### 1.6 Write Var request layout ✅

A write op adds a "data region" after offset 31. Taking `WriteVarReal` (`StartByteAddress=1`, 4-byte payload) as the example:

| Offset | Field | Description |
|:--:|------|------|
| 0..1 | `03 00` | TPKT fixed header |
| **2..3** | `{PDULength:X4}` | **whole-frame length** = `{Frame:fixed}` + `{WriteValue:len}` = 35 + payload length ✅ (6-19: 35+4=39=`0x27`) |
| 4..6 | `02 F0 80` | COTP DT |
| 7..10 | `32 01 00 00` | S7 header |
| 11..12 | `{TransactionID:X4}` | PDU reference (auto-increment) |
| 13..14 | `00 0E` | parameter-region length = 14 |
| **15..16** | `{DataLen:X4}` | **data-region length** = `{WriteValue:len}` + 4 ✅ (6-20: 4+4=8=`0x0008`) |
| 17 | `05` | function code = Write Var |
| 18 | `01` | item count = 1 |
| 19..21 | `12 0A 10` | S7ANY addressing spec |
| 22 | `08` | transport size (REAL) |
| **23..24** | `{ItemLength:X4}` | element count = `ByteCount/4` ✅ (6-21: `0x0001`) |
| 25..26 | `{DBNumber:X4}` | DB block number |
| 27 | `{Area:X2}` | area code |
| 28..30 | `{AddrHi/Mid/Lo}` | S7 address (**excludes BitOffset**) ✅ (6-22: 1→`00 00 08`) |
| 31 | `00` | data-region reserved byte |
| **32** | `03/04/07` | **data-region transport size TS_Res** ✅ (6-23: REAL=`0x07`) |
| **33..34** | `{DataBits:X4}` | bit length = `{WriteValue:len}*8` (write-bit op hardcodes `00 01`) ✅ (6-24: `0x0020`; 6-32: `0x0001`) |
| **35..** | `{WriteValue:raw}` | payload bytes ✅ (6-25: `41 20 00 00` = IEEE-754 big-endian `10.0`) |

**Fixed segment = 35 bytes** (hence `{Frame:fixed}` evaluates to 35) ✅ (6-18: 35 + 4 = 39; 6-27: 35 + 1 = 36)

> `{Frame:fixed}` is a primitive introduced by [ADR-0012](../../adr/0012-derivedlength-template-primitives-and-trial-render.md) *zh*: the template's fixed-segment length is computed by the engine, replacing the historically hand-written `+35` magic number — after adding/removing a fixed byte you no longer need to hand-edit the offset.

## 2. Field-by-field protocol-config mapping

### 2.1 transport and the device side ✅

```jsonc
// s7-1200.json —— the protocol declares only the type
"transport": { "type": "Tcp" }
```

```jsonc
// tags.json —— the device side gives host/port/timeout (example: PLC_1200)
{
  "id": "PLC_1200",
  "protocol": "s7-1200",
  "connection": { "host": "127.0.0.1", "port": 102, "timeoutMs": 5000 },
  "requestTimeoutMs": 2000
}
```

- S7 communication uses the fixed port **102**; `port` must be written explicitly on the device side (a protocol-level `defaultPort` only makes sense for protocols like Modbus)
- both `timeoutMs` (connect timeout) and `requestTimeoutMs` (single request-response timeout) are **required and must be > 0**, otherwise the save-time validation rejects them

### 2.2 inputs (protocol-level input section) ✅

| Variable | Example | Meaning | Who overrides it |
|------|:--:|------|------|
| `StartByteAddress` | 0 | start **byte** address | **tag** `variables` (each tag's distinct address goes here) |
| `ByteCount` | 2 | data **byte** span | tag `variables` |
| `BitOffset` | 0 | bit offset within the byte (0~7) | tag `bitOffset` |
| `DBNumber` | 1 | DB block number | tag `variables` |
| `Area` | 132 | area code (enumerable, see the table below) | tag `variables` |
| `TransactionID` | auto | PDU reference, `autoIncrement` | automatic by the engine |

`Area` enum (the config carries display labels, so the WebUI offers a direct dropdown):

| Value | Area | S7-side notation |
|:--:|------|------|
| 129 | Input PE | `I0.0` / `IB0` |
| 130 | Output PA | `Q0.0` / `QB0` |
| 131 | Flags M | `M0.0` / `MB0` |
| 132 | Data block DB | `DB1.DBX0.0` / `DB1.DBW0` |

### 2.3 outputs: byte address → S7 bit address ✅

```jsonc
"AddrLo":  { "strategy": "derivedLength", "expr": "(StartByteAddress * 8) % 256" },
"AddrMid": { "strategy": "derivedLength", "expr": "((StartByteAddress * 8) / 256) % 256" },
"AddrHi":  { "strategy": "derivedLength", "expr": "(StartByteAddress * 8) / 65536" }
```

- S7ANY addresses are **24-bit, in units of bits**: `S7addr = byteAddr × 8 + bitOffset`
- the three outputs are the decomposition of those 24 bits (written big-endian into template bytes 28/29/30)
- the **write-bit** op's three exprs add a `+ BitOffset` term (see [§3.2](#32-readwrite-asymmetry-bitoffset-only-applies-to-write-addresses-))

### 2.4 handshake (two steps, see §1.3)

| Step | Frame len | `validCondition` | Judgment meaning |
|------|:--:|------|------|
| `COTP_CR` | 22 (`0x16`) | `resp[5] == 0xD0` | COTP connection confirm |
| `S7_Setup` | 25 (`0x19`) | `resp[8] == 0x03` | S7-layer Ack_Data |

### 2.5 operations (8)

| Operation | kind | Purpose | transport size (request) | length expr |
|------|:--:|------|:--:|------|
| `ReadVarBit` | read | read 1 byte (bit extracted on the MyProt side) | `03` | `ByteCount` |
| `ReadVarWord` | read | read 16-bit | `04` | `ByteCount / 2` |

| `ReadVarReal` | read | read float | `08` | `ByteCount / 4` |
| `WriteVarBit` | write | write 1 bit | `01` | fixed `00 01` |

## 3. Byte-address wiring: the one thing to grasp first about this protocol (v1.27)

### 3.1 Why "byte address" instead of "S7 bit address"

S7's absolute address (S7ANY) is a **bit address**: `DB1.DBD4`'s S7 address is `32` (= 4×8), while `DB1.DBX0.1` is `1`. Hand-computing such addresses is an error hotspot.

MyProt's convention:

> **Always write a "byte address" in the tag (= `StartByteAddress`); leave the ×8 work to the protocol outputs.**

| What you want to read | tag `StartByteAddress` | S7 address MyProt emits (`AddrHi Mid Lo`) | Basis |
|------|:--:|------|:--:|
| `DB1.DBW0` | 0 | `00 00 00` | 🧮 |
| `DB1.DBD4` (4 bytes) | 4 | `00 00 20` (=4×8=32=0x20) | ✅ 6-5 |
| any byte 1000 | 1000 | `00 1F 40` (=8000=0x1F40) | ✅ 6-8 |
| any byte 8192 | 8192 | `01 00 00` (=65536) | ✅ 6-12 |

The third and fourth rows together prove the `AddrMid`/`AddrHi` carry is correct (crossing 256, crossing 65536).

### 3.2 Read/write asymmetry: `BitOffset` only applies to write addresses ✅

This is **the easiest semantic difference to trip over**; two assertions nail it down:

| Scenario | `BitOffset` | Address result | Basis |
|------|:--:|------|:--:|
| **read** bit (`ReadVarBit`) | 3 | `00 00 00` — **not part of the address** | ✅ 6-15 |
| **write** bit (`WriteVarBit`) | 3 | `AddrLo = 03` (`0×8+3`) | ✅ 6-31 |

> Why designed this way: for a **read**, the whole byte comes back and bit extraction is done on the tag side (`bitOffset` + `finalType: Bool`, see [§3.3](#33-tag-side-three-examples-)); for a **write**, the bit position must be encoded into the S7 address so the PLC knows which bit to write.
>
> Likewise, a normal word/float **write** op's address also excludes `BitOffset` ✅ (6-22).

### 3.3 Tag-side three examples ✅

The three S7 tags in `configs/tags.json` cover three typical data points:

| Tag | S7-side object | `operation` | `StartByteAddress` | `ByteCount` | `bitOffset` | `finalType` | write op |
|------|------|------|:--:|:--:|:--:|------|------|
| `PLC_1200.DBW0` | `DB1.DBW0` | `ReadVarWord` | 0 | 2 | — | `UInt16` | `WriteVarWord` |
| `PLC_1200.DBD4` | `DB1.DBD4` | `ReadVarWord` | 4 | 4 | — | `Float` | `WriteVarWord` |
| `PLC_1200.DBX0_1` | `DB1.DBX0.1` | `ReadVarBit` | 0 | 1 | 1 | `Bool` | `WriteVarBit` |

Two points worth noting:

1. **all three tags set `coalesce: false`** — an explicit Schema convention: "single-address reads (e.g. S7 `ReadVar*`) set `false`" ([Config_Schema §tag fields](../Config_Schema.md)). S7 issues an independent Read/Write Var per data point.
2. **`DBD4` can read 4 bytes even with `ReadVarWord`** 🧮: `ByteCount/2 = 2` WORDs × 2 bytes = 4 bytes, the **same byte count** as `ReadVarReal`'s `1` REAL × 4 bytes; the only difference is the transport-size field (`04` vs `08`). If you want the request to state REAL explicitly (some PLCs / capture tools give a clearer type hint), just switch `operation`/`writeOperation` to `ReadVarReal`/`WriteVarReal`. The Float interpretation is done by the tag `finalType` + protocol `dataByteOrder: BigEndian`.

## 4. Per-operation "config ↔ byte" mapping

### 4.1 The four read siblings ✅

The request frames are structurally identical; only 3 spots vary by type:

| Operation | TS(offset 22) | Length(23..24) | frame len | assertion |
|------|:--:|------|:--:|------|
| `ReadVarBit` | `03` | `ByteCount` (=1) | 31 | 6-14, 6-16 |
| `ReadVarWord` | `04` | `ByteCount / 2` | 31 | 6-2, 6-3, 6-4 |
| `ReadVarDWord` | `06` | `ByteCount / 4` | 31 | 6-10, 6-11 |
| `ReadVarReal` | `08` | `ByteCount / 4` | 31 | 6-6, 6-7, 6-9 |

**Who decides how many bytes to read**: tag `variables.ByteCount` → the `Length` expression → the byte count PLC returns; then `finalType` decides how to interpret those N bytes (`Bool`/`UInt16`/`Float`/`ByteArray`…).

### 4.2 The four write siblings ✅

Common part (`WriteValue` is the template's `{WriteValue:raw}` payload placeholder, injected at write-path runtime):

| Field(offset) | expression | Word | DWord | Real | Bit |
|------|------|:--:|:--:|:--:|:--:|
| `PDULength`(2..3) | `{Frame:fixed} + {WriteValue:len}` | 35+len | 35+len | 35+len ✅(6-19) | 35+1 ✅(6-28) |
| `DataLen`(15..16) | `{WriteValue:len} + 4` | ✅(same) | | ✅(6-20: `0x0008`) | ✅(6-29: `0x0005`) |
| function code(17) | constant | `05` | `05` | `05` | `05` |
| TS(22) | constant | `04` | `06` | `08` | `01` ✅(6-30) |
| `ItemLength`(23..24) | `ByteCount / 2` or `/4` | `ByteCount/2` | `ByteCount/4` | ✅(6-21) | fixed `00 01` |
| address(28..30) | see §2.3 (**excludes BitOffset**) | ✅ | | ✅(6-22) | incl. BitOffset ✅(6-31) |
| reserved(31) | constant `00` | | | | |
| `TS_Res`(32) | constant | `04` | `04` | `07` ✅(6-23) | `03` ✅(6-30) |
| `DataBits`(33..34) | `{WriteValue:len} * 8` | ✅ | | ✅(6-24: `0x0020`) | fixed `00 01` ✅(6-32) |
| payload(35..) | `{WriteValue:raw}` | ✅ | | ✅(6-25) | ✅(6-33) |

**Full worked example (`WriteVarReal`, write `10.0` to `DB1.DBD4`)** 🧮:

```
length: 3.0 → bytes 40 40 00 00      10.0 → bytes 41 20 00 00
frame len = 35 + 4 = 39 = 0x0027 ✅ 6-19
DataLen = 4 + 4 = 8 = 0x0008 ✅ 6-20
ItemLength = ByteCount/4 = 1 ✅ 6-21     AddrLo = (4*8)%256 = 0x20 ✅
TS_Res = 0x07(REAL) ✅ 6-23              DataBits = 4*8 = 0x0020 ✅ 6-24
payload = 41 20 00 00 ✅ 6-25
```

### 4.3 Two transport-size tables (do not mix them)

| Location | Values | Meanings used by this repo |
|------|:--:|------|
| **request item TS** (offset 22) | `03` | read by byte (bit taken on the MyProt side) ✅ 6-16 |
| | `04` / `06` / `08` | WORD / DWORD / REAL ✅ 6-3, 6-10, 6-9 |
| | `01` | write bit (BIT) ✅ 6-30 |
| **data-region TS_Res** (write request offset 32) | `03` | bit ✅ 6-30 |
| | `04` | byte/word/dword |
| | `07` | REAL ✅ 6-23 |

> This repo uses only the values above; other S7 types (`INT`/`DINT`/`DATE`/structs, etc.) are not covered in the config — add op templates per the S7 spec when needed.

## 5. Response judgment and exception semantics

### 5.1 The judgment is a single byte

```jsonc
"responseParser": { "validCondition": "resp[21] == 0xFF", "dataStartIndex": 25, "dataLengthExpr": "" }
```

- `resp[21]` is the item's **return code**: `0xFF` = success ✅ (see the §1.5 layout derivation)
- fail → `quality = Bad` + `lastError` recorded (consistent with Modbus's "judge validity only" strategy)

### 5.2 `dataLengthExpr` empty = "take to the frame end" 🧮

S7 read ops **deliberately** omit `dataLengthExpr`:

```
when dataLengthExpr is empty, semantics = frame length − dataStartIndex
```

(defined in the `responseParser.dataLengthExpr` comment of `src/Core/include/MyProt/Core/Config.hpp`)

Because the TPKT length field already gives the whole-frame length ✅ (§1.2), the data region is naturally "from 25 to the frame end", no expression needed. **This is yet another S7-vs-Modbus parsing difference**: Modbus locates via the `ByteCount` field.

### 5.3 v1 limitation: error class / error code not parsed

Response offsets 17 (error class) and 18 (error code) are **not parsed currently**: `resp[21] != 0xFF` simply means `Bad`, without distinguishing "address out of range / type mismatch / insufficient resource" and other S7 errors.

To refine this, extend `validCondition` or (more thoroughly) add an "error-code extraction" capability — such extensions should first go into the [ROADMAP](../../ROADMAP.md) *zh*.

| # | Setting | Location (TIA Portal) | Consequence if not done |
|:--:|------|------|------|
| 1 | check **Permit access with PUT/GET from remote partners** | Device properties → Protection & security → Connection mechanism | the session reaches Setup then is rejected; all read/write bytes go Bad |
| 2 | on the target DB **turn off "optimized block access"** | DB properties → Properties → uncheck "optimized block access" | only symbolic addressing works; S7ANY absolute-address reads fail |
| 3 | confirm the **rack/slot** (default 0/2) | corresponds to handshake template `C2 02 01 02` | cannot connect (COTP CC does not return `0xD0`) |

> These three are field experience (no PLC here to prove it): items 1 and 2 are the general prerequisites for S7-1200 DB read/write over S7comm; item 3, if it needs changing, is edited directly in `s7-1200.json`'s `handshake[0]` template and saved (the save-time trial-render validation runs again ✅).

### 6.2 Three choices for the controlled end

| Choice | Can verify directly | Notes |
|------|:--:|------|
| Real S7-1200 | ✅ recommended | just point `tags.json`'s `host` at the PLC |
| S7-PLCSIM / a third-party S7 server (e.g. Snap7 Server) | ✅ usable | likewise only change `host`/`port`; note its PDU and TSAP behavior may differ from a real device ⚠️ |
| **MyProt's built-in simulator** | ❌ **not applicable to S7** | see below |

**Why the built-in simulator cannot emulate S7** (source-based, not guesswork):

- `simulation.listenPort > 0` in `configs/server.json` is the master switch, but `ApplyRuntimeSync` **takes only the 0th protocol in the protocol list** as the simulator's "syntax basis", and its behavior is entirely decided by `simulation.operations` in `server.json` (`src/App/RuntimeGlue.cpp`);
- the 0th protocol in filename lexicographic order is `modbus-tcp` (the App startup log prints only one "simulator modbus-tcp listening" line ✅ observed);
- the simulation data model is a **register array** (`registerCount` / `initialValues[regNum]`), which does not correspond to S7's "DB + byte/bit address" semantics.

> Conclusion: **for S7 integration use a real PLC or a third-party S7 server**. If an S7 simulation is ever built, it needs a new data model and response-synthesis strategy (better registered in the [ROADMAP](../../ROADMAP.md) *zh*).

## 7. Common troubleshooting

| Symptom | Check first | Basis |
|------|------|------|
| connection fails / stuck `Connecting` | `host`/`port` (must be 102), firewall, whether the PLC permits PUT/GET | ⚠️ §6.1 |
| connects but drops right after handshake | COTP dest TSAP (`C2 02 01 02`) mismatches the real rack/slot | ⚠️ §1.3 |
| handshake succeeds but all tags `Bad` | ①is the DB's "optimized block access" off; ②do `DBNumber`/`Area` point right; ③is the address out of range | ⚠️ §6.1 |
| only bit tags correct, word/float wrong | `dataByteOrder` (should be `BigEndian`), whether `finalType` matches `ByteCount` (float must be 4 bytes) | 🧮 §3.3 |
| read value is "misaligned" bytes | `StartByteAddress` was written as an S7 bit address (multiplied by 8 too many) | ✅ §3.1 |
| write succeeds but the PLC-side value doesn't change | write-bit vs write-word `BitOffset` semantics (read excludes, write includes); whether `ItemLength`/`DataBits` match the payload length | ✅ §3.2, §4.2 |
| config save rejected | look at the numbered list in the popup (frame-length consistency / derived-length expr / reference integrity, etc.) | ✅ [§5.1 validation surfacing](../../webui.md) *zh* |
| frame-length errors | `framing.lengthIncludesHeader` must be `true`, `headerLength: 4`; the write template's `PDULength` must use `{Frame:fixed} + {WriteValue:len}` | ✅ §1.2, §1.6 |
