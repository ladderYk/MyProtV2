## 0. 30 秒速览

```jsonc
// s7-1200.json 顶层 7 个字段
{
  "transport":     "Tcp（端口由设备侧 102 指定）",   // 1. 传输层
  "framing":       "LengthField at offset 2（= TPKT 长度域）", // 2. 帧定界
  "dataByteOrder": "BigEndian",                     // 3. S7 数据区字节序
  "inputs":        "StartByteAddress / ByteCount / BitOffset / DBNumber / Area / TransactionID",
  "outputs":       "AddrLo / AddrMid / AddrHi（字节地址 → S7 位地址换算）",
  "handshake":     "COTP_CR → S7_Setup（两步）",      // 6. 会话建立
  "operations":    "8 个：Read/Write × Bit|Word|DWord|Real"
}
```

**MyProt 的 S7 配置 = 一份"字节流剧本"**：

| 配置位置 | 对应 S7 规范的哪一层 |
|------|------|
| `framing` | TPKT 头（4 字节）的长度域定位 |
| `handshake[0]` | COTP Connection Request → Connection Confirm |
| `handshake[1]` | S7 Setup Communication（协商 PDU 长度） |
| `operations[*].requestTemplate` | 固定头 + `Read Var` / `Write Var` 请求参数区 + 地址区 |
| `operations[*].responseParser` | 返回码判定 + 数据区起点 |
| `outputs.AddrHi/Mid/Lo` | **字节地址 → S7 位地址**（`字节<<3`）换算 |

**一句话理解本适配的核心价值**：你在标签里只写**字节地址**（`DB1.DBD4` → `StartByteAddress: 4`），MyProt 负责把它换算成 S7 的三字节位地址 `00 00 20` ✅（`4 × 8 = 32 = 0x20`）。

## 1. 帧结构回顾（MyProt 视角）

### 1.1 三层嵌套

所有 S7-1200 报文（含握手与读写）都是同一副骨架：

```
┌────────────┬─────────┬──────────────────────────────────────────┐
│ TPKT (4B)  │ COTP(3B)│ S7 PDU (10B 头 + 参数区 + 数据区)          │
│ 03 00 LLLL │ 02 F0 80│ 32 <ROSCTR> ...                          │
└────────────┴─────────┴──────────────────────────────────────────┘
  ↑ framing 从这里取长度
```

| 层 | 字节 | 说明 |
|------|:--:|------|
| TPKT | `03 00 <总长2B>` | 固定头 `03 00`；**长度 = 整帧字节数（含这 4 字节）** —— 这就是 `lengthIncludesHeader: true` 的由来 |
| COTP | `02 F0 80` | 数据 PDU：`02`=头长、`F0`=DT、`80`=TPDU-NR 与 EOT |
| S7 | `32 <ROSCTR> …` | `32`=S7comm 协议标识；`ROSCTR`：`0x01`=Job(请求)、`0x03`=Ack_Data(应答) |

### 1.2 TPKT 长度域与 `framing` 的对应 ✅

```jsonc
"framing": {
  "type": "LengthField",
  "lengthFieldOffset": 2,     // TPKT 长度域从第 2 字节开始
  "lengthFieldLength": 2,     // 占 2 字节
  "lengthIncludesHeader": true,  // ★ 长度值含 TPKT 4 字节头（S7 特有）
  "headerLength": 4,             // ★ 头长 = TPKT 4 字节
  "byteOrder": "BigEndian",
  "lengthAdjustment": 0,
  "maxFrameSize": 4096        // MyProt 侧接收上限（与 PLC 协商的 PDU 无关）
}
```

**怎么用**：读到长度域值 `N` → 整帧就是 `N` 字节（不再加减 header）✅

- 读 1 个 WORD 的请求：`03 00 00 1F` → `0x1F = 31` 字节 ✅（6-2）
- 写 1 个 REAL 的请求：`03 00 00 27` → `0x27 = 39` 字节 ✅（6-19）
- 写 1 位的请求：`03 00 00 24` → `0x24 = 36` 字节 ✅（6-28）

> 对比 Modbus：Modbus 的 `lengthIncludesHeader` 为 `false` 且 `headerLength: 6`（长度只算 PDU）。**两协议的 framing 差异就在这两行**——这也是为什么 framing 是本项目最容易配错、也最早拦截的字段（保存期试算校验，见 [ADR-0012](../adr/0012-derivedlength-template-primitives-and-trial-render.md)）。

### 1.3 握手：两步建立会话

**第 1 步 —— COTP 连接请求（CR）**，整帧 22 字节（`0x16`）🧮：

```
03 00 00 16             TPKT：总长 22
11 E0 00 00 00 01 00     COTP CR：头长 0x11、类型 0xE0(CR)、目的引用 0000、源引用 0001、class 00
C1 02 01 00             参数 C1(源 TSAP)   长度 2 值 01 00
C2 02 01 02             参数 C2(目的 TSAP) 长度 2 值 01 02   ← ★ 机架/槽位编码，换机型要改这行
C0 01 0A                参数 C0(TPDU 尺寸) 长度 1 值 0A = 1024 字节
```

判定：`validCondition: "resp[5] == 0xD0"` —— 即期待 **CC（Connection Confirm，0xD0）**✅（偏移 5 是 COTP 类型字节 🧮）

**第 2 步 —— S7 Setup Communication**，整帧 25 字节（`0x19`）🧮：

```
03 00 00 19             TPKT：总长 25
02 F0 80                COTP DT
32 01 00 00 00 01 00 08 00 00   S7 头：Job + 引用 0001 + 参数长 8 + 数据长 0
F0 00 00 08 00 01 03 C0         参数：功能 0xF0(Setup) + 保留 + MaxAmQ(8) + MaxAmQ(1) + 协商 PDU 03C0=960
```

判定：`validCondition: "resp[8] == 0x03"` —— 即应答的 `ROSCTR = 0x03`（Ack_Data）✅

> ⚠️ 握手模板里的 `C2 02 01 02`（目的 TSAP）与 `03 C0`（960 字节 PDU）是**面向 S7-1200 的取值**；若换成 300/400 或非默认机架槽位，需按实机修改这两处（本仓未做机型自适应）。

### 1.4 Read Var 请求布局（逐字段）✅

以 `ReadVarWord` 为例（`StartByteAddress=4`、`ByteCount=2`、`DBNumber=1`、`Area=132`）：

| 偏移 | 字节 | 字段 | 取值来源 |
|:--:|------|------|------|
| 0..3 | `03 00 00 1F` | TPKT | 常量 + `{PDULength}`? 否——读操作是**常量 0x1F**（读请求定长 31） |
| 4..6 | `02 F0 80` | COTP DT | 常量 |
| 7..10 | `32 01 00 00` | S7 头：协议标识 + ROSCTR(Job) + 保留 | 常量 |
| 11..12 | `{TransactionID:X4}` | PDU 引用 | `source=auto`，`autoIncrement`（seed=1）|
| 13..14 | `00 0E` | 参数区长度 = 14 | 常量（读请求参数区固定）|
| 15..16 | `00 00` | 数据区长度 = 0 | 常量（读请求无数据区）|
| 17 | `04` | 功能码 = Read Var | 常量 |
| 18 | `01` | item 数 = 1 | 常量（单标签单 item）|
| 19 | `12` | 变量规格类型 = S7ANY | 常量 |
| 20 | `0A` | 后续地址规格长度 = 10 | 常量 |
| 21 | `10` | 寻址语法 ID = S7ANY（绝对地址）| 常量 |
| **22** | `03/04/06/08` | **传输尺寸 TS** | 常量，见 [§4.3](#43-两张-transport-size-表别混) |
| **23..24** | `{Length:X4}` | **元素数量** | `derivedLength`：`ByteCount/2`、`ByteCount/4` 或 `ByteCount` ✅（6-4/6-7/6-11/6-14）|
| 25..26 | `{DBNumber:X4}` | DB 块号 | 标签 `variables.DBNumber`（示例 = 1）|
| 27 | `{Area:X2}` | 区域码 | 标签 `variables.Area`（示例 = 132=DB）|
| 28 | `{AddrHi:X2}` | S7 地址高字节 | `(字节地址*8)/65536` ✅（6-12：8192→`01`）|
| 29 | `{AddrMid:X2}` | S7 地址中字节 | `((字节地址*8)/256)%256` ✅（6-8：1000→`1F`）|
| 30 | `{AddrLo:X2}` | S7 地址低字节 | `(字节地址*8)%256` ✅（6-5：4→`20`）|

**总长恒为 31** ✅（6-2）——读操作的 TPKT 长度与元素数无关（长度信息在 23..24）。

### 1.5 Read Var 响应布局 🧮

```
0..3    TPKT（长度域 = 整帧长）
4..6    02 F0 80（COTP DT）
7       32        协议标识
8       03        ROSCTR = Ack_Data   ← 握手第 2 步就判这个字节
9..10   00 00     冗余标识
11..12  PDU 引用（回显请求的 TransactionID）
13..14  参数区长度 = 00 04
15..16  数据区长度 = 00 04 + 2×N（N 为元素数）
17      错误类别    ← 本仓不解析
18      错误码      ← 本仓不解析
19      04        功能码（Read Var）
20      01        item 数
21      FF        返回码：0xFF = 成功     ← ★ validCondition：resp[21] == 0xFF
22      04/06/08  数据区传输尺寸
23..24  长度（BIT 类型以位计，其余为元素数）
25..    数据区（载荷）                    ← ★ dataStartIndex = 25
```

由此可直接推出：**读 1 个 WORD 的响应 = 25 + 2 = 27 字节**；**读 1 个 DWORD/REAL = 25 + 4 = 29 字节** 🧮

### 1.6 Write Var 请求布局 ✅

写操作在偏移 31 之后多了"数据区"。以 `WriteVarReal`（`StartByteAddress=1`、载荷 4 字节）为例：

| 偏移 | 字段 | 说明 |
|:--:|------|------|
| 0..1 | `03 00` | TPKT 固定头 |
| **2..3** | `{PDULength:X4}` | **整帧长** = `{Frame:fixed}` + `{WriteValue:len}` = 35 + 载荷长 ✅（6-19：35+4=39=`0x27`）|
| 4..6 | `02 F0 80` | COTP DT |
| 7..10 | `32 01 00 00` | S7 头 |
| 11..12 | `{TransactionID:X4}` | PDU 引用（自增）|
| 13..14 | `00 0E` | 参数区长度 = 14 |
| **15..16** | `{DataLen:X4}` | **数据区长度** = `{WriteValue:len}` + 4 ✅（6-20：4+4=8=`0x0008`）|
| 17 | `05` | 功能码 = Write Var |
| 18 | `01` | item 数 = 1 |
| 19..21 | `12 0A 10` | S7ANY 寻址规格 |
| 22 | `08` | 传输尺寸（REAL）|
| **23..24** | `{ItemLength:X4}` | 元素数量 = `ByteCount/4` ✅（6-21：`0x0001`）|
| 25..26 | `{DBNumber:X4}` | DB 块号 |
| 27 | `{Area:X2}` | 区域码 |
| 28..30 | `{AddrHi/Mid/Lo}` | S7 地址（**不含 BitOffset**）✅（6-22：1→`00 00 08`）|
| 31 | `00` | 数据区保留字节 |
| **32** | `03/04/07` | **数据区传输尺寸 TS_Res** ✅（6-23：REAL=`0x07`）|
| **33..34** | `{DataBits:X4}` | 位长度 = `{WriteValue:len}*8`（写位操作硬编码 `00 01`）✅（6-24：`0x0020`；6-32：`0x0001`）|
| **35..** | `{WriteValue:raw}` | 载荷字节 ✅（6-25：`41 20 00 00` = IEEE-754 大端 `10.0`）|

**固定段 = 35 字节**（因此 `{Frame:fixed}` 的值为 35）✅（6-18：35 + 4 = 39；6-27：35 + 1 = 36）

> `{Frame:fixed}` 是 [ADR-0012](../adr/0012-derivedlength-template-primitives-and-trial-render.md) 引入的原语：模板固定段长度由引擎核算，替代历史上手写的 `+35` 魔数——增删一个固定字节后无需再人工改偏移。

## 2. 协议配置逐字段对照

### 2.1 transport 与设备侧 ✅

```jsonc
// s7-1200.json —— 协议只声明类型
"transport": { "type": "Tcp" }
```

```jsonc
// tags.json —— 设备侧给出 host/port/超时（示例：PLC_1200）
{
  "id": "PLC_1200",
  "protocol": "s7-1200",
  "connection": { "host": "127.0.0.1", "port": 102, "timeoutMs": 5000 },
  "requestTimeoutMs": 2000
}
```

- S7 通信固定端口 **102**，`port` 必须显式写在设备侧（协议级 `defaultPort` 仅对 Modbus 这类协议有意义）
- `timeoutMs`（连接超时）与 `requestTimeoutMs`（单次请求-应答超时）都是**必填且必须 > 0**，否则保存期即被校验拒绝

### 2.2 inputs（协议级输入段）✅

| 变量 | 示例值 | 含义 | 谁覆盖它 |
|------|:--:|------|------|
| `StartByteAddress` | 0 | 起始**字节**地址 | **标签** `variables`（每个标签不同的地址就写在这）|
| `ByteCount` | 2 | 数据**字节**跨度 | 标签 `variables` |
| `BitOffset` | 0 | 字节内位偏移（0~7）| 标签 `bitOffset` |
| `DBNumber` | 1 | DB 块号 | 标签 `variables` |
| `Area` | 132 | 区域码（可枚举，见下表）| 标签 `variables` |
| `TransactionID` | auto | PDU 引用，`autoIncrement` 自增 | 引擎自动 |

`Area` 枚举（配置里带中文标签，WebUI 直接下拉选择）：

| 值 | 区域 | S7 侧写法 |
|:--:|------|------|
| 129 | 输入 PE | `I0.0` / `IB0` |
| 130 | 输出 PA | `Q0.0` / `QB0` |
| 131 | 标志位 M | `M0.0` / `MB0` |
| 132 | 数据块 DB | `DB1.DBX0.0` / `DB1.DBW0` |

### 2.3 outputs：字节地址 → S7 位地址 ✅

```jsonc
"AddrLo":  { "strategy": "derivedLength", "expr": "(StartByteAddress * 8) % 256" },
"AddrMid": { "strategy": "derivedLength", "expr": "((StartByteAddress * 8) / 256) % 256" },
"AddrHi":  { "strategy": "derivedLength", "expr": "(StartByteAddress * 8) / 65536" }
```

- S7ANY 地址是 **24 位、以位为单位**：`S7地址 = 字节地址 × 8 + 位偏移`
- 三个 outputs 就是这 24 位的拆解（大端序写入模板的 28/29/30 字节）
- **写位操作**的三条 expr 多一项 `+ BitOffset`（见 [§3.2](#32-读写不对称bitoffset-只管写地址-)）

### 2.4 handshake（两步，见 §1.3）

| 步骤 | 帧长 | `validCondition` | 判定含义 |
|------|:--:|------|------|
| `COTP_CR` | 22 (`0x16`) | `resp[5] == 0xD0` | COTP 连接确认 |
| `S7_Setup` | 25 (`0x19`) | `resp[8] == 0x03` | S7 层 Ack_Data |

### 2.5 operations（8 个）

| 操作 | kind | 用途 | 传输尺寸(请求) | 长度表达式 |
|------|:--:|------|:--:|------|
| `ReadVarBit` | read | 读 1 字节（位在 MyProt 侧提取）| `03` | `ByteCount` |
| `ReadVarWord` | read | 读 16 位 | `04` | `ByteCount / 2` |
| `ReadVarDWord` | read | 读 32 位 | `06` | `ByteCount / 4` |
| `ReadVarReal` | read | 读浮点 | `08` | `ByteCount / 4` |
| `WriteVarBit` | write | 写 1 位 | `01` | 固定 `00 01` |
| `WriteVarWord` | write | 写 16 位 | `04` | `ByteCount / 2` |
| `WriteVarDWord` | write | 写 32 位 | `06` | `ByteCount / 4` |
| `WriteVarReal` | write | 写浮点 | `08` | `ByteCount / 4` |

## 3. 字节地址接线：本协议最该先懂的一件事（v1.27）

### 3.1 为什么用"字节地址"而不是"S7 位地址"

S7 的绝对地址（S7ANY）是**位地址**：`DB1.DBD4` 的 S7 地址是 `32`（= 4×8），而 `DB1.DBX0.1` 是 `1`。手算这类地址是差错高发区。

MyProt 的约定：

> **标签里永远写"字节地址"（=`StartByteAddress`），乘 8 的工作交给协议 outputs。**

| 想读的东西 | 标签 `StartByteAddress` | 引擎发出的 S7 地址（`AddrHi Mid Lo`）| 依据 |
|------|:--:|------|:--:|
| `DB1.DBW0` | 0 | `00 00 00` | 🧮 |
| `DB1.DBD4`（4 字节）| 4 | `00 00 20`（=4×8=32=0x20）| ✅ 6-5 |
| 任意字节 1000 | 1000 | `00 1F 40`（=8000=0x1F40）| ✅ 6-8 |
| 任意字节 8192 | 8192 | `01 00 00`（=65536）| ✅ 6-12 |

第三条与第四条同时证明了 `AddrMid`/`AddrHi` 的进位正确（跨 256、跨 65536）。

### 3.2 读/写不对称：`BitOffset` 只管写地址 ✅

这是**最容易踩的语义差异**，两条断言把它钉死了：

| 场景 | `BitOffset` | 地址结果 | 依据 |
|------|:--:|------|:--:|
| **读**位（`ReadVarBit`）| 3 | `00 00 00` —— **不参与地址** | ✅ 6-15 |
| **写**位（`WriteVarBit`）| 3 | `AddrLo = 03`（`0×8+3`）| ✅ 6-31 |

> 为什么这样设计：**读**整个字节回来，位提取由标签侧完成（`bitOffset` + `finalType: Bool`，见 [§3.3](#33-标签侧三例对照)）；而**写**必须把位位置编码进 S7 地址，PLC 才知道写哪一位。
>
> 同理，普通字/浮点**写**操作的地址也不含 `BitOffset` ✅（6-22）。

### 3.3 标签侧三例对照 ✅

`configs/tags.json` 里三个 S7 标签覆盖了三种典型数据点：

| 标签 | S7 侧对象 | `operation` | `StartByteAddress` | `ByteCount` | `bitOffset` | `finalType` | 写操作 |
|------|------|------|:--:|:--:|:--:|------|------|
| `PLC_1200.DBW0` | `DB1.DBW0` | `ReadVarWord` | 0 | 2 | — | `UInt16` | `WriteVarWord` |
| `PLC_1200.DBD4` | `DB1.DBD4` | `ReadVarWord` | 4 | 4 | — | `Float` | `WriteVarWord` |
| `PLC_1200.DBX0_1` | `DB1.DBX0.1` | `ReadVarBit` | 0 | 1 | 1 | `Bool` | `WriteVarBit` |

两点值得说明：

1. **三个标签都写了 `coalesce: false`** —— 这是 Schema 的明确约定："单地址读（如 S7 `ReadVar*`）设 `false`"（[Config_Schema §标签字段](../Config_Schema.md)）。S7 每个数据点独立发一次 Read/Write Var。
2. **`DBD4` 用 `ReadVarWord` 也能读 4 字节** 🧮：`ByteCount/2 = 2` 个 WORD × 2 字节 = 4 字节，与 `ReadVarReal` 的 `1` 个 REAL × 4 字节**字节数一致**；差异只在传输尺寸字段（`04` vs `08`）。若希望请求里明确表达 REAL（部分 PLC/抓包工具的类型提示更直观），把 `operation`/`writeOperation` 换成 `ReadVarReal`/`WriteVarReal` 即可。Float 的解释由标签 `finalType` + 协议 `dataByteOrder: BigEndian` 完成。

## 4. 各操作"配置 ↔ 字节"对照

### 4.1 读四兄弟 ✅

请求帧结构完全相同，只有 3 处随类型变化：

| 操作 | TS(偏移22) | Length(23..24) | 帧长 | 断言 |
|------|:--:|------|:--:|------|
| `ReadVarBit` | `03` | `ByteCount`（=1）| 31 | 6-14、6-16 |
| `ReadVarWord` | `04` | `ByteCount / 2` | 31 | 6-2、6-3、6-4 |
| `ReadVarDWord` | `06` | `ByteCount / 4` | 31 | 6-10、6-11 |
| `ReadVarReal` | `08` | `ByteCount / 4` | 31 | 6-6、6-7、6-9 |

**读多少字节由谁决定**：标签 `variables.ByteCount` → `Length` 表达式 → PLC 返回的字节数；随后 `finalType` 决定把这 N 字节解释成什么类型（`Bool`/`UInt16`/`Float`/`ByteArray`…）。

### 4.2 写四兄弟 ✅

公共部分（`WriteValue` 是模板里的 `{WriteValue:raw}` 载荷占位符，由写路径运行时注入）：

| 字段(偏移) | 表达式 | Word | DWord | Real | Bit |
|------|------|:--:|:--:|:--:|:--:|
| `PDULength`(2..3) | `{Frame:fixed} + {WriteValue:len}` | 35+len | 35+len | 35+len ✅(6-19) | 35+1 ✅(6-28) |
| `DataLen`(15..16) | `{WriteValue:len} + 4` | ✅（同上式）| | ✅(6-20：`0x0008`) | ✅(6-29：`0x0005`) |
| 功能码(17) | 常量 | `05` | `05` | `05` | `05` |
| TS(22) | 常量 | `04` | `06` | `08` | `01` ✅(6-30) |
| `ItemLength`(23..24) | `ByteCount / 2` 或 `/4` | `ByteCount/2` | `ByteCount/4` | ✅(6-21) | 固定 `00 01` |
| 地址(28..30) | 见 §2.3（**不含 BitOffset**）| ✅ | | ✅(6-22) | 含 BitOffset ✅(6-31) |
| 保留(31) | 常量 `00` | | | | |
| `TS_Res`(32) | 常量 | `04` | `04` | `07` ✅(6-23) | `03` ✅(6-30) |
| `DataBits`(33..34) | `{WriteValue:len} * 8` | ✅ | | ✅(6-24：`0x0020`) | 固定 `00 01` ✅(6-32) |
| 载荷(35..) | `{WriteValue:raw}` | ✅ | | ✅(6-25) | ✅(6-33) |

**完整算例（`WriteVarReal`，写 `10.0` 到 `DB1.DBD4`）** 🧮：

```
长度：3.0 → 字节 40 40 00 00      10.0 → 字节 41 20 00 00
帧长 = 35 + 4 = 39 = 0x0027 ✅ 6-19
DataLen = 4 + 4 = 8 = 0x0008 ✅ 6-20
ItemLength = ByteCount/4 = 1 ✅ 6-21     AddrLo = (4*8)%256 = 0x20 ✅
TS_Res = 0x07(REAL) ✅ 6-23              DataBits = 4*8 = 0x0020 ✅ 6-24
载荷 = 41 20 00 00 ✅ 6-25
```

### 4.3 两张 transport size 表（别混）

| 位置 | 取值 | 本仓用到的含义 |
|------|:--:|------|
| **请求 item 的 TS**（偏移 22）| `03` | 按字节读（MyProt 侧再取位）✅ 6-16 |
| | `04` / `06` / `08` | WORD / DWORD / REAL ✅ 6-3、6-10、6-9 |
| | `01` | 写位（BIT）✅ 6-30 |
| **数据区 TS_Res**（写请求偏移 32）| `03` | 位 ✅ 6-30 |
| | `04` | 字节/字/双字 |
| | `07` | REAL ✅ 6-23 |

> 本仓只用到了上表这些值；其它 S7 类型（`INT`/`DINT`/`DATE`/结构体等）未在配置中覆盖，需要时按 S7 规范新增操作模板。

## 5. 响应判定与异常语义

### 5.1 判定就一个字节

```jsonc
"responseParser": { "validCondition": "resp[21] == 0xFF", "dataStartIndex": 25, "dataLengthExpr": "" }
```

- `resp[21]` 是 item 的**返回码**：`0xFF` = 成功 ✅（见 §1.5 布局推导）
- 不通过 → `quality = Bad` + `lastError` 记录（与 Modbus 的"只判 valid"策略一致）

### 5.2 `dataLengthExpr` 留空 = "取到帧尾" 🧮

S7 读操作**故意**没写 `dataLengthExpr`：

```
dataLengthExpr 为空时的语义 = 帧长 − dataStartIndex
```

（定义见 `src/Core/include/MyProt/Core/Config.hpp` 的 `responseParser.dataLengthExpr` 注释）

因为 TPKT 长度域已经把整帧长度给定了 ✅（§1.2），数据区天然是"25 到帧尾"，无需再算表达式。**这是 S7 与 Modbus 在解析上的又一差异**：Modbus 用 `ByteCount` 字段定位。

### 5.3 v1 局限：不解析错误类别/错误码

响应偏移 17（错误类别）、18（错误码）**目前不解析**：`resp[21] != 0xFF` 即 `Bad`，不会区分"地址越界/类型不符/资源不足"等 S7 错误。

需要细化时，可扩展 `validCondition` 或（更彻底）新增一个"错误码提取"能力——这类扩展应先进 [ROADMAP](../ROADMAP.md)。

## 6. 实战联调

### 6.1 PLC 侧准备（三项，缺一必失败）⚠️

| # | 设置 | 位置（TIA Portal）| 不做的后果 |
|:--:|------|------|------|
| 1 | 勾选**允许来自远程伙伴的 PUT/GET 通信访问** | 设备属性 → 防护与安全 → 连接机制 | 会话建到 Setup 后被拒，读写字节全 Bad |
| 2 | 目标 DB **关闭"优化的块访问"** | DB 属性 → 属性 → 取消「优化的块访问」 | 只能符号寻址，S7ANY 绝对地址读取失败 |
| 3 | 确认**机架/槽位**（默认 0/2）| 与握手模板 `C2 02 01 02` 对应 | 连不上（COTP CC 不返回 `0xD0`）|

> 这三项是实机经验（本仓无 PLC 可证）：第 1、2 项是 S7-1200 使用 S7comm 读写 DB 的通用前提；第 3 项如需改动，直接编辑 `s7-1200.json` 的 `handshake[0]` 模板并保存（保存期会重新试算校验 ✅）。

### 6.2 被控端三种选择

| 选择 | 能否直接验证 | 说明 |
|------|:--:|------|
| 真实 S7-1200 | ✅ 推荐 | 改 `tags.json` 的 `host` 指向 PLC 即可 |
| S7-PLCSIM / 第三方 S7 服务器（如 Snap7 Server）| ✅ 可用 | 同样只改 `host`/`port`；注意其 PDU 与 TSAP 行为可能与实机有差异 ⚠️ |
| **MyProt 自带仿真器** | ❌ **不适用于 S7** | 见下 |

**为什么自带仿真器不能模拟 S7**（源码依据，非猜测）：

- `configs/server.json` 的 `simulation.listenPort > 0` 是总开关，但 `ApplyRuntimeSync` **只取协议列表的第 0 个协议**作为仿真器的"语法依据"，行为完全由 `server.json` 的 `simulation.operations` 决定（`src/App/RuntimeGlue.cpp`）；
- 第 0 个协议按文件名字典序是 `modbus-tcp`（App 启动日志只打印一条"仿真器 modbus-tcp 已监听"✅ 实测）；
- 仿真数据模型是**寄存器数组**（`registerCount` / `initialValues[寄存器号]`），与 S7 的"DB + 字节/位地址"语义不对应。

> 结论：**S7 联调请用真实 PLC 或第三方 S7 服务器**。若将来要做 S7 仿真，需要新的数据模型与响应合成策略（登记在 [ROADMAP](../ROADMAP.md) 更合适）。

### 6.3 MyProt 侧：三步走

1. 确认 `configs/server.json` 的 `simulation.listenPort`（不影响 S7 连接，但决定是否同时起 Modbus 仿真器）
2. 改 `configs/tags.json`：设备 `PLC_1200` 的 `connection.host/port` 指向被控端
3. 启动 `MyProt.App`，看日志：
   ```
   [Config] 已加载协议 2 个, 设备 2 个, 标签 15 个     ← s7-1200.json 被加载
   [Lifecycle] 设备 PLC_1200 生命周期 New → Connecting
   [Channel]  TCP 连接开始: <host>:102 (timeout=5000ms, channel=PLC_1200)
   ```


## 7. 常见排错

| 现象 | 优先检查 | 依据 |
|------|------|------|
| 连接建立失败 / 一直 `Connecting` | `host`/`port`（必须 102）、防火墙、PLC 是否允许 PUT/GET | ⚠️ §6.1 |
| 连上但握手后立刻断 | COTP 目的 TSAP（`C2 02 01 02`）与实机机架/槽位不符 | ⚠️ §1.3 |
| 握手成功但所有标签 `Bad` | ①DB 是否关闭"优化的块访问"；②`DBNumber`/`Area` 是否指对；③地址是否越界 | ⚠️ §6.1 |
| 只有位标签对、字/浮点不对 | `dataByteOrder`（应为 `BigEndian`）、`finalType` 与 `ByteCount` 是否匹配（浮点必须 4 字节）| 🧮 §3.3 |
| 读到的值是"错位"的字节 | `StartByteAddress` 写成了 S7 位地址（多乘了 8）| ✅ §3.1 |
| 写成功但 PLC 侧值没变 | 写位 vs 写字的 `BitOffset` 语义（读不含、写含）；`ItemLength`/`DataBits` 是否与载荷长度一致 | ✅ §3.2、§4.2 |
| 保存配置被拒 | 看弹窗里的编号清单（帧长一致性 / 派生长度 expr / 引用完整性等）| ✅ [§5.1 校验可见化](../webui.md) |
| 帧长类报错 | `framing.lengthIncludesHeader` 必须为 `true`、`headerLength: 4`；写模板的 `PDULength` 必须用 `{Frame:fixed} + {WriteValue:len}` | ✅ §1.2、§1.6 |
