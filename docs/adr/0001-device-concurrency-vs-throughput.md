## 背景

现行架构有两处无法同时成立的约定：
1. **并发安全策略**（architecture/03 §5.3）：同一设备的请求经 `asio::strand` **严格串行**，以保证请求/响应帧不交叉错乱。
2. **性能目标**（architecture/05）：单设备 QPS ≥ 500 read/s，同时端到端延迟 P50 ≤ 5ms。

严格串行下，单设备吞吐上限 = `1000 / 单次往返耗时`。若 P50 延迟 5ms，理论上限仅 200 read/s——**500 QPS 与 5ms 延迟在串行模型下互斥**。此外"read/s" 的统计口径未定义：按"物理请求次数"还是"读取的标签数"计算，结论完全不同。

这不是笔误，而是"稳定性优先"与"性能指标"尚未和解。本 ADR 给出裁决。

## 决策驱动因素

- **帧完整性不可妥协**：单 socket 上请求/响应交错是协议网关最严重的事故类型（数据张冠李戴且难以复现），默认模型必须天然免疫。
- **指标必须可验证**：性能目标要能被 benchmarks 直接复现，口径需无歧义。
- **协议差异要可表达**：Modbus TCP 有事务 ID 可并发，许多串口/私有协议只能一问一答——模型需按协议区分，而非一刀切。
- **实现成本可控**：v1 不应为极限吞吐承担乱序相关的复杂度。

## 备选方案

### 方案 A：维持严格串行 + 修正指标口径

保留 strand 串行，把性能指标从"物理请求 read/s"改为"**标签 tags/s**"，承认单物理请求速率受往返时延约束。
- 优点：零实现成本；帧安全有数学保证；指标诚实。
- 缺点：不解决"单设备大量标签、单次往返很慢"场景的绝对吞吐问题。

### 方案 B：串行 + 积极请求合并（与 A 组合）

在串行基础上，把吞吐的主手段放到 **TagGrouper/MergeRequest 请求合并**：同设备、同操作、连续地址的标签合并为**一个物理请求**，一次往返取回 N 个标签。吞吐以"合并后 tags/request × 请求速率"衡量。
- 优点：不破坏帧完整性即可成倍提升有效吞吐；合并逻辑已在设计中（Gateway 模块）。Modbus 单次可读 125 寄存器，合并收益巨大。
- 缺点：仅对"地址连续可合并"的标签有效；离散标签退化为方案 A。

### 方案 C：协议声明式多会话并发（v2 可选）

协议配置增加 `maxConcurrentRequests`（默认 1）；> 1 时 ChannelManager 允许同一设备有多个 in-flight 请求，引擎通过**事务 ID 关联**响应与请求（需 framing 层暴露事务 ID 提取）。适用于明确支持并发的协议（如 Modbus TCP 多事务、S7 多 PDU）。
- 优点：真正突破串行上限；按协议 opt-in，默认仍安全。
- 缺点：需要响应关联机制、乱序/超时/错配的完整处理；部分设备固件对并发事务支持不佳，需逐设备验证；实现与测试成本显著。

### 方案 D：单连接流水线（pipelining）

不等待响应即发送下一请求，完全靠事务 ID 乱序关联。
- 优点：理论吞吐最高。
- 缺点：绝大多数工业设备按序应答、甚至不支持未决多请求，流水线收益小、风险大；与"稳定优先"冲突。**不推荐**。

## 权衡对比

| 维度 | A 串行 | A+B 串行+合并 | C 声明式并发 | D 流水线 |
|------|:--:|:--:|:--:|:--:|
| 帧完整性保证 | ✓ | ✓ | 中（依赖关联正确性） | ✗ |
| 单设备有效吞吐 | 低 | 中—高 | 高 | 最高 |
| 实现成本 | 低 | 低（已在设计内） | 高 | 很高 |
| 协议适用性 | 全部 | 可合并协议受益 | 仅支持并发事务的协议 | 极窄 |
| 可验证性 | 高 | 高 | 中 | 低 |

## 决策

**v1 基线采用 A+B**：
1. 维持每设备 strand 严格串行，不做任何并发放宽。
2. 把请求合并作为吞吐主手段，TagGrouper 的合并策略纳入性能验收路径。
3. **修订性能目标**（替代 architecture/05 原表）：

| 指标 | 修订目标 | 测试条件 |
|------|------|------|
| 单设备有效吞吐 | ≥ 500 **tags/s** | Modbus TCP，连续地址合并，loopback |
| 单设备物理请求速率 | ≥ 200 req/s | 同上，不可合并的离散标签 |
| 端到端延迟 P50 / P99 | ≤ 5ms / ≤ 50ms | 单物理请求，不含网络，**仅统计成功且无重试、无重连**的请求 |
| 100 设备并发吞吐衰减 | ≤ 10% | 100 独立 loopback |
| 内存（100 设备 / 1000 标签）| ≤ 50MB RSS | 稳态 |
| 启动时间 | ≤ 2s | 含 100 设备连接 |

> 原"单设备 QPS ≥ 500 read/s"作废：在串行 + 5ms 延迟约束下不可达，且 read/s 口径不明。新口径以 tags/s（合并语义）为准，物理请求速率单列。

> **延迟口径与超时的关系**（见 [ADR-0004](./0004-timeout-retry-budget.md)）：P50/P99 仅统计**健康路径**（成功且无重试、无重连的单物理请求）；`device.requestTimeoutMs`（默认 3000ms，2026-08-24 起收敛为设备级配置点，原为 `operation.timeoutMs`）是**故障检测看门狗**，不是期望延迟。超时、重试、重连属故障路径，不计入该延迟分布，而由 deadline 与熔断约束。二者正交，P99 ≤ 50ms 与 3000ms 看门狗不矛盾。

**v2 预留方案 C**：在 Config_Schema §9 已占位 `maxConcurrentRequests`（v1 加载器强制为 1）。启用前需先交付：framing 层事务 ID 提取、响应关联表、错误/超时丢弃策略，以及针对目标设备的并发兼容性验证。

**方案 D 不采纳**，记录在案以免重复讨论。

## 影响

- `architecture/03` §5.3：无需改动（串行策略不变），但应补一句"吞吐经由请求合并提升，见 ADR-0001"。
- `architecture/05` 性能目标表：按上表替换。
- `modules/05_Gateway` TagGrouper：合并策略从"优化项"升级为"验收关键路径"，需补合并率统计（merged_tags / total_tags）进 Metrics。
- `modules/07_WebApi` Metrics：新增 `myprot_merge_ratio{device=...}`。
- Config_Schema：`maxConcurrentRequests` 保持预留，v1 校验器对 >1 报 Warning 并回退到 1。

## 复核触发条件

出现以下任一情况时重新评估方案 C：
- 实际项目中存在"单设备 > 200 个不可合并离散标签且 scanRate < 1s"的硬需求；
- 目标协议/设备被验证支持稳定的多事务并发（提供 loopback 压测证据）；
- tags/s 口径被下游（MQTT/时序库容量规划）证明不足以描述需求。
